03 · Accessible design and code

Making accessibility part of how we work

Over three years, I fixed accessibility problems across four VA.gov apps. I started by pointing them out in design reviews, then tracked down and fixed the underlying code. I also added tests to catch issues like screen readers repeating a warning or keyboard users losing their place.

Situation
Accessibility fixes across 4 apps
My role
Design reviews, code fixes, and tests
Team
Partnered with VA accessibility specialists
Outcome
Fixes shipped; tests added

The problem

People using screen readers, keyboards, or enlarged text can encounter barriers others may not notice. Many surfaced just before launch, when fixes were disruptive, and a one-page fix didn’t stop the same problem from appearing elsewhere.

What I did

Fixed shared parts, not just individual pages

I corrected headings, tables, and keyboard focus after page updates, then moved four apps to shared link components. I also advocated for a reusable fix to how screen readers announce page titles.

Found why a warning was repeated

A warning I designed was announced twice by VoiceOver, Apple’s screen reader. I traced the duplicate announcement to two lines of code, corrected them, and added tests to catch the problem if it returns.

Tested it myself

Before review, I check with VoiceOver, enlarged text, and axe, an automated accessibility checker. I also add tests to catch broken fixes.

The result

Code fixes across 4 apps

Over 3 years, I moved from checking contrast and zoom to fixing the code behind the issues.

Screen-reader fix shipped

The VoiceOver improvements went live in August 2026, and several accessibility issues identified by VA were resolved.

Tests catch broken fixes

Automated tests flag when a later change breaks an accessibility fix.
